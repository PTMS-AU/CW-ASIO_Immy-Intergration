1. Overview

This integration connects ImmyBot to ConnectWise RMM (the platform formerly known as Continuum/Command, now branded as ASIO) so that:

  • ConnectWise companies show up in ImmyBot as clients, mappable to ImmyBot tenants.
  • ConnectWise-managed endpoints surface as agents with live online status (via the ASIO heartbeat endpoint).
  • An ImmyBot computer can be matched to its ConnectWise endpoint automatically (inventory identification).
  • The ConnectWise ASIO agent itself can be deployed by ImmyBot, with per-tenant install tokens fetched at install time.

It is built as a self-contained ImmyBot Dynamic Integration script — one PowerShell file, no external module — paired with a software package consisting of detection, dynamic-versions, install, uninstall, and test scripts.

Regional note. This deployment targets the Australia ASIO region (openapi.service.auplatform.connectwise.com). The integration works regionally — only the API Endpoint URL field changes for other regions (EU/US).

2. Prerequisites

2.1 ConnectWise side

  • An ASIO partner account with API access enabled.
  • An ASIO Integration key (Client ID + Client Secret) generated under Integrations → Asio Integrations → Integrate → Generate.
  • The API key must have the following OAuth scopes granted:
    • platform.companies.read
    • platform.sites.read
    • platform.devices.read
    • platform.agent-token.read
    • platform.asset.read
    • platform.agent.read
    • platform.automation.create (required for RunScript — see §7.2)
    Easiest path: tick all available scopes when generating the key. The integration requests the read scopes above plus one write scope (automation.create for RunScript), so over-granting on the key side is harmless.

2.2 ImmyBot side

  • ImmyBot instance with access to the Integrations area.
  • Permission to create and edit Software entries and Deployments.

3. Installing the integration

  1. In ConnectWise ASIO, generate a Client ID and Client Secret with the scopes listed in §2. Copy the secret immediately — ASIO only shows it once.
  2. In ImmyBot, go to Integrations → New Dynamic Integration.
  3. Paste the contents of ConnectWiseRMM-Integration.ps1 as the integration script. Give it a recognisable name (e.g. Connectwise ASIO).
  4. Configure the three integration parameters:
    ParameterValue (AU region)
    API Endpoint URLhttps://openapi.service.auplatform.connectwise.com
    Client IDFrom ASIO key generation
    Client SecretFrom ASIO key generation
  5. Save and initialise. The integration's HealthCheck performs an OAuth token exchange and one companies read — if it goes Healthy, the credentials and scopes are confirmed good.

If HealthCheck fails with a token error, see Troubleshooting. The most common cause is a missing scope or a secret that wasn't copied completely from the ASIO UI.

4. Installing the software package

Create a new Software entry in ImmyBot called ConnectWise RMM (Asio) (or similar). Then configure each section:

4.1 Detection

  • Detection Method: Custom Detection Script
  • Script: paste Detect-Asio.ps1

The detection script returns a fixed 1.0.0 when the ASIO agent is installed, the ITSPlatform service is running, and the registry contains a populated privateendpointid (proving the agent is registered with ConnectWise). Anything else returns $null — meaning ImmyBot will treat the machine as "not installed" and remediate.

4.2 Dynamic Versions

  • Enable Use dynamic versions
  • Script: paste Get-AsioAgentDownloadLink.ps1
  • Desired Version: Latest

This script returns a fixed version of 1.0.0 paired with the generic (non-tokenized) barebone MSI URL. Both detection and desired version agree on 1.0.0, so once installed, the machine reports compliant and stays compliant — ASIO updates the agent itself in the background.

4.3 Agent Integration

  • Under Advanced, set Agent Integration = your Connectwise ASIO integration.

This is the link that lets the install script call Get-IntegrationAgentInstallToken. Without it, installs fail with "Get-IntegrationAgentInstallToken returned nothing."

4.4 Install Script

Install Script: paste Install-Asio.ps1. Repair Strategy: Uninstall/Install (or Install Over — either works because detection is binary).

4.5 Uninstall Script

Uninstall Script: paste Uninstall-Asio.ps1.
Set the Detection String parameter to: SaazOnDemand|ITSPlatform

The script uses ImmyBot's Detect-Software with this regex to find the installed product entry and parse its UninstallString. After uninstall, a cleanup block removes the ITSPlatform and ITSPlatformManager services and the registry keys, which the MSI sometimes leaves behind.

4.6 Test Script

  • Enable Test Required
  • Test failed error: ITSPlatform service not running or agent not registered with ASIO
  • Test Script: paste Test-Asio.ps1

The test loops for up to 5 minutes after install, retrying every 15 seconds and attempting to start the service if it's not running yet. It only passes when both the service is Running and privateendpointid is populated.

5. Mapping tenants to ConnectWise companies

After the integration goes Healthy, ImmyBot pulls the ConnectWise company list. Go to Integration → Clients tab and map each ImmyBot tenant to its corresponding ConnectWise company.

Why this matters. The install-token capability uses the mapped company ID to generate a tenant-scoped install token. If a tenant isn't mapped, the install script throws "GetTenantInstallToken received no mapped company id."

Tenants only need to be mapped once. Re-mapping is harmless. Listing additional companies that you don't intend to deploy to is fine — only mapped tenants are touched.

7. API scopes and auth model

7.1 Auth flow

The integration uses OAuth2 client_credentials:

  1. POST /v1/token with a JSON body containing grant_type, client_id, client_secret, and a space-separated scope string.
  2. Read access_token from the response.
  3. Send Authorization: Bearer <access_token> on each API call.

A fresh token is fetched per capability invocation; tokens are not cached between invocations.

7.2 Scope set requested

All token requests in the integration request the same read-scope string:

platform.companies.read platform.sites.read platform.devices.read platform.agent-token.read platform.asset.read platform.agent.read

This is deliberate over-granting per call. Earlier iterations requested narrower scopes per capability, and we hit a class of bug where a token minted for one scope was used against an endpoint gated by another (e.g. agent-token scope used for a sites lookup → 403 "client has no access"). Requesting the full read surface on every token removes that whole failure class. The trade-off is that we're not running least-privilege at the call level — but the key itself already has these scopes granted, so there's no additional risk.

Write-scope exception: RunScript

IRunScriptProvider is the sole capability that requires a write scope. Its token request adds platform.automation.create to the scope string — the schedule-tasks endpoint is a POST that creates ephemeral automation tasks. Every other capability in the integration remains read-only. The exception is acceptable because RunScript is an inherently mutating operation (it runs a script on a remote endpoint), so a write scope is the correct representation of what it does.

8. Installer hosting

The dynamic-versions script returns this download URL:

https://platinumfilestorage.blob.core.windows.net/installer/asio/ITSPlatform.msi

This is our own Azure Blob Storage mirror of the ConnectWise generic barebone MSI, not ConnectWise's CDN. The original ConnectWise URL —

https://setup.auplatform.connectwise.com/windows/BareboneAgent/32/ITSagent/MSI/setup

— serves the file via a redirect chain that ImmyBot's downloader doesn't follow cleanly, causing install actions to fail to retrieve the MSI.

This is a maintenance dependency. If ConnectWise releases a new barebone installer and we don't refresh the blob, deployments will silently install stale bootstrappers. Refresh process:

  1. Download the current generic MSI from setup.auplatform.connectwise.com/windows/BareboneAgent/32/ITSagent/MSI/setup (use a browser or curl -L to follow redirects).
  2. Upload to the blob container, replacing the existing ITSPlatform.msi.
  3. No script changes required — the URL is constant.

Recommend doing this on a quarterly cadence, or whenever ConnectWise announces an agent update.

9. Troubleshooting

9.1 Integration won't go Healthy

HealthCheck errorLikely causeAction

A mismatch returns 403 "client has no access" even when scopes are correct.Ensure the heartbeat request uses resourceType=endpoints. This is already correct in the current integration script; if you see this error after modifying the script, check the query-string parameter.

9.2 Install fails: "Get-IntegrationAgentInstallToken returned nothing"

  • Confirm the Software entry has Agent Integration set under Advanced (§4.3).
  • Confirm the tenant is mapped to a ConnectWise company under Integration → Clients (§5).
  • Check the integration's audit log for the most recent GetTenantInstallToken call. It will name the failing step:
    • Step 1 = OAuth token request failed → scope/credential issue.
    • Step 2 = site lookup failed → typically 403 "client has no access", meaning a missing scope (we now request all read scopes, so this should not recur).
    • Step 3 = token generation failed → check the response body for the actual error; could be a malformed company/site ID.

9.3 Install fails: "This package is configured for workstations only"

The install script gates on Win32_OperatingSystem.ProductType -ne 1 (workstation). Server install would require validating the correct SYSTEM= property value for ASIO server mode, which has not been done yet. Servers should be excluded from the deployment's target filter, or a separate server package should be created once the server install property is known.

9.4 Device shows the script's source code instead of a GUID under inventory

The GetInventoryScript block must use Invoke-ImmyCommand { ... }, not return { ... }. The latter returns the scriptblock AST itself to ImmyBot, which then renders it as inventory data instead of executing it.

Cleanup: if a device already shows the AST blob and the inventory doesn't refresh, temporarily change the inventory script to return $null, force inventory re-identification, then switch back to the real script.

9.5 Detection shows installed but check-in reports failed

This was symptomatic of SupportsRunningScripts:$true being set on emitted agents when the integration didn't implement the script-execution capability. The current integration emits $false; if the symptom recurs, verify the flag in New-IntegrationAgent.

9.6 ITSPlatform service or registry remains after uninstall

The uninstall script includes a cleanup block (sc.exe delete on the services, Remove-Item -Recurse on the registry keys). If detection still reports installed after an uninstall, run a fresh uninstall — the cleanup block is idempotent.

10. Design decisions & trade-offs

10.1 Why a fixed 1.0.0 version instead of dynamic versions?

The ASIO agent self-updates after install. The version installed today is not the version installed tomorrow. Returning the real agent version would cause ImmyBot to perceive constant drift, and in the worst case attempt downgrades when the running agent is newer than the MSI bootstrapper. Collapsing to a binary "installed-and-healthy / not-installed" check matches the agent's actual lifecycle.

10.2 Why is the token requested at install time, not version-determination time?

Earlier iterations called Get-IntegrationAgentInstallToken during the dynamic-versions script, so every machine doing a version check exercised the token endpoint. A token failure (transient API issue, scope problem) would then block detection across the whole fleet. Moving the call to install-time means the token endpoint is only exercised on machines being actively installed — version checks now never touch ConnectWise.

10.3 Why hedge the OAuth scope string?

See §7.2. Net: one broad scope string per token, applied across every call, removes the class of "token scoped for X used against endpoint gated by Y" bugs that bit us three different ways during development.

10.4 Why a self-hosted blob mirror for the MSI?

See §8. ConnectWise's generic URL serves the file via a redirect chain ImmyBot can't follow. The blob mirror is a direct download. Trade-off: we own the freshness of the file (see the refresh process in §8).

10.5 Why workstation-only install?

The server install needs SYSTEM= set to a value other than desktop (likely server, but unconfirmed). Rather than guess and risk installing workstation mode on production servers, the install gates on ProductType == 1. To add server support: validate the correct property value with ConnectWise, then either branch the install script on ProductType, or create a separate server software package.

11. Change history

v1.1

  • RunScript capability — added IRunScriptProvider via POST /api/platform/v2/automation/endpoints/schedule-tasks. Ephemeral script execution on ASIO endpoints.
  • Write-scope exception — RunScript requires platform.automation.create, making it the only capability that carries a write scope. All other capabilities remain read-only.
  • Heartbeat resourceType correction — the heartbeat endpoint requires resourceType=endpoints. Earlier iterations omitted or used incorrect values, causing 403 errors.

v1.0 (initial release)

Significant decisions captured during development:

  • OAuth flow — confirmed as POST /v1/token → Bearer access_token. The earlier "secret-is-the-bearer" model in some legacy docs is not what the ASIO spec describes.
  • Device listing verb — the OpenAPI spec declares POST; live testing against the AU tenant requires GET-with-body. The integration uses GET. Comment in the code warns against "fixing" it.
  • Pagination — device listing is paginated at 500 endpoints/page via Link: rel="next". The integration follows the header until exhausted.
  • Scope mismatch class of bug — install-token site lookup, heartbeat, and GetAgents all 403'd at various points because tokens were minted with narrower scopes than the endpoints they then called. Resolved by standardising on one broad read-scope string for every token request.
  • SupportsRunningScripts — flipped from $true to $false to match what the integration actually implements. Setting it true caused ImmyBot to attempt script execution through ASIO and fail check-in.
  • Token property name — confirmed as TOKEN=<guid> from the ASIO scope list and silent-install doc. Plus SYSTEM=desktop for install mode.
Maintained alongside the integration scripts. Update this doc whenever the integration interface or installer hosting changes.
